# Official TrailBase password-auth contract

## Decision and version boundary

The newer explicit decision selects **official TrailBase0.35.9 or newer as the supported minimum**, without version autodetection, a version-setting option or a private capability. The reproducible native fixture targets **0.35.9**, commit `a106ce6338f9831140c92ac16e051901ed92d576`; **trailbase JS0.14.3** and the pinned Supabase reference are unchanged. Private prototypes remain historical private evidence, not dependencies or an active parity workstream.

**This minimum is an operator/deployment invariant, not something the SDK verifies.** Every actual logout handler/replica must serve the supported native contract and the same intended auth realm/session store, including throughout a client's lifetime and any rollback. **Older, mixed-version or rolled-back deployments are unsupported and can return misleading matching200 acknowledgements without authenticated deletion.** Response/body checks do not discover a version or make those deployments safe. There is no discovery/precheck/cache, administrator API, hidden fallback or automatic replay. Later official releases still need qualification of the documented wire behavior; a minimum is not runtime proof of all future versions.

This is a private development contract, not a public SDK release, full Supabase compatibility or feature/security/release signoff. The current artifact has Linux/x64 runtime proof; other native platforms have release-metadata evidence only until exercised. See the [MVP plan](MVP_PLAN.md), [test plan OGL01–OGL06](TEST_PLAN.md), [release checklist](RELEASE_QUALIFICATION.md) and [source-bound progress ledger](progress.json). The original official0358 demo/assets/data/six containers are unchanged and are **not** upgraded or certified by these repository edits.

## Selected supported subset and honest failure behavior

| Operation | Development contract over the supported official minimum |
| --- | --- |
| `signUp({email,password})` | One native registration with matching password repeat. Successful registration returns `{data:{user:null,session:null},error:null}`: no fabricated identity/session. A prompt to check mail does not prove delivery or confirmation. |
| Duplicate pending signup | Native409 remains an error with null user/session. No automatic retry, success conversion, password replacement, deduplication or identity repair. Follow a previously delivered genuine link if available; do not repeatedly register. |
| SMTP failure | Native424 remains an error/no session. A pending identity can remain; retry can return409. This differs from the measured reference new-user transaction rollback. A healthy control/restored SMTP does not prove the failed identity recovered. |
| Confirmation/resend | Follow actual delivered native mail, then explicitly log in. No SDK `auth.resend`, account repair, password recovery or admin-confirmation flow. Generic native trigger200 is not proof of delivery or a supported pending-identity recovery path. No throttle bypass/timestamp edits. |
| `signInWithPassword` | Genuine confirmed email/password credentials, mapped only to the narrow supported fields. Failed/unconfirmed/unknown credentials cannot become a session. No metadata/MFA/OAuth/phone/URL callback-session adoption. |
| `getSession` / persistence | Awaited owned hydration/cached credentials/request-time renewal; cached claims are not live authorization. Browser localStorage and Node per-client memory defaults; no cross-tab or shared server-request session guarantee. |
| `getUser` / `refreshSession` | Argument-free live native validation/guarded renewal. Status can rotate credentials; refresh retains the actual original refresh credential. Only native refresh401 is terminal. No Supabase status/timing/token-rotation parity claim. |
| Explicit `signOut({scope:'local'})` | Immediately invalidate local generation/state, remove only owned storage and send one native POST with captured refresh JSON. Require native200; errors stay observable. Local is not owner-wide revocation. |
| Default/global `signOut()` / `{scope:'global'}` with captured credentials | Never silently local. One fixed-origin native GET with captured Bearer **and exact request `Content-Type: application/json`**, no body/refresh/CSRF headers, omitted cookies and manual redirects. Accept only nonredirect200, expected request URL if supplied, UTF8 `text/plain` and complete exact ten-byte `logged out` receipt through EOF. Bound global request plus receipt delivery at10s; own reader/abort/timer cleanup. Under the minimum invariant, this acknowledges native owner-wide refresh-session DELETE, not merely local cleanup. |
| Empty-client signOut | Local idempotent `{error:null}` with zero remote requests. **Not** an acknowledgement that server sessions were deleted. |
| Notifications | Only `INITIAL_SESSION`, `SIGNED_IN`, `TOKEN_REFRESHED`, `SIGNED_OUT`. Defensive snapshots/owned unsubscribe. SIGNED_OUT immediately reports null; async owned-key removal is awaited before signOut settles, not promised inside the callback. SIGNED_IN/TOKEN_REFRESHED follow persistence. No immediate remote-device event guarantee. |

Other options/methods remain rejected or absent. `scope:'others'`, private/global capability flags and version options remain unsupported; no private registration/resend/receipt endpoint or protocol emulator is used. Existing hydration/storage serialization, compensation/fail-closed latch, generation guards and per-scope single-flight policy remain in force. Held old-owner delivery cannot erase a later committed login or produce late old-owner events. Failed owned storage removal remains an error even when the native operation succeeded; externally repairing disk does not unlatch an old client.

### Failures, expiry and what acknowledgement does not prove

- Redirects/opaque/followed/foreign responses, wrong MIME, malformed/truncated/extra bytes and body deadlines do not acknowledge. Receipt failures return sanitized `AuthGlobalSignOutUnconfirmedError`; failed requests remain request errors; native non200 statuses remain actionable errors. No response-body secrets are echoed. Custom fetch is trusted to honor credential/redirect/abort options; a returned response check cannot undo a request that a custom transport already sent elsewhere.
- SignOut clears owned local state independently of remote success. Lost/failed replies can occur **after actual DELETE**. Caller error/timeout/abort does not prove rollback, cancellation or quiescence, and causes no replay or automatic local fallback.
- Logout uses captured JWT and **does not silently renew it**. A genuinely expired native JWT returns401/no DELETE/error after local clearing, even if its refresh session remains valid. This is not native refresh401's terminal policy. Reference SDK proactive renewal and401/403/404 local-cleanup suppression are separate measured policies, not evidence that an authenticated DELETE occurred; do not invent identical acknowledgement semantics.
- Deleting refresh sessions does **not** instantly invalidate stateless access JWTs, prevent later password login, deliver immediate remote events or protect a racing new session from an outstanding global DELETE. Unexpired JWTs retain their native residual authorization until actual expiry/leeway. Scope is the native account/auth realm/session store, not independent backends. A client-local generation guard does not cancel server work or make login/logout globally atomic.

## Why global acknowledgement needs an upstream capability

Official0359 supplies the capability in its [GET logout handler](https://github.com/trailbaseio/trailbase/blob/a106ce6338f9831140c92ac16e051901ed92d576/crates/core/src/auth/api/logout.rs): mandatory authenticated `User`, awaited owner-wide session deletion, then a nonredirect plaintext200 for **exact request JSON Content-Type**. Accept alone or JSON-with-charset is not the same request contract; an explicit native redirect URI takes precedence. Invalid/expired callers and database failures cannot become successful deletion acknowledgements. The SDK uses only the fixed nonredirect route, not redirect following or an owner-wide emulation using local calls.

Historically, the [official0358 handler](https://github.com/trailbaseio/trailbase/blob/05238c02b54aabb483e9f6224b5e014d40e88a5d/crates/core/src/auth/api/logout.rs) used `Option<User>`. A rootless route could return the **same200/body/MIME to an invalid/expired caller with no DELETE**. Root/explicit redirects were likewise not authenticated receipts. These real historical observations are preserved, not rewritten as0359 behavior. Matching receipt bytes on an unsupported old/mixed/rolled-back deployment can still mislead; strict parsing is **not version detection**.
