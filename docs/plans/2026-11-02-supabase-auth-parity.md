## Reference targets and actual proof boundaries

Reference: pinned Supabase Auth **v2.197.0**, official Supabase JS2.117.2 and aligned fixture configuration. Root reviewed the pinned source (and reports the same relevant current-master code); that source review is not a new runtime test. Official documentation is rolling; version-specific source and actual configured responses take precedence over simplified examples.

1. **Confirmation-enabled ordinary new signup:** successful `signUp` returns a real user and `session:null`; password login is denied before confirmation. Existing reference characterization proves this ordinary flow. Our successful `{user:null,session:null}` remains a real capability gap/explicit outstanding exception, **not full parity**. Do not invent a purportedly real newly-created user/UUID or use privileged browser lookup to hide the missing native register return. This is different from Supabase's intentional anti-enumeration placeholder for a confirmed duplicate (case4), not a claim that Supabase never fabricates IDs.

2. **New signup + detected SMTP-send failure:** pinned `signup.go` wraps new-user creation and confirmation send in a database transaction; a send error returns an error and rolls back the new user. This is **not** the existing-pending-account retry case. Existing `smtp.test.ts` asserts/has historically observed Supabase500, null user/session and later successful retry/real confirmation/login; it does **not** independently prove every database rollback or no-mail-delivery postcondition. A native failure earlier in this mixed test can prevent later reference assertions from running. Add explicit real database/session/mail assertions before claiming those guarantees. SMTP acceptance followed by loss/spam is not a detected send failure: no inferred rollback or guaranteed delivery. A database transaction cannot retract externally accepted mail.

3. **Existing unconfirmed account:** repeat signup reuses the identity and original password, even if a different password is supplied, and attempts confirmation sending subject to configured throttles. Standard public resend is `auth.resend({type:'signup',email})`. Existing reference characterization proves same-user-ID success **or exact429 `over_email_send_rate_limit`**, no session, confirmation-required login, then genuine confirmation/original-password login and replacement-password denial. Pinned `/resend` returns generic HTTP200 `{}` for an unknown or already-confirmed address without sending a new confirmation; anti-enumeration/no-send behavior needs dedicated runtime tests. Resend is a target, not a currently implemented SDK method.

4. **Confirmed duplicate is configuration-dependent:** with both email and SMS confirmation enabled, the aligned reference fixture returns an obfuscated/sanitized user, null session and leaves the password unchanged; existing characterization proves this. If either email or SMS autoconfirm is enabled, pinned source returns HTTP422 `user_already_exists`, even with the phone provider disabled. That configuration matrix still needs runtime proof. Do not universalize faux-user success or silently change fixture/live configuration.

5. **Rates:** preserve observed server429/cooldown behavior. Documentation lists a default60-second signup confirmation interval; project settings are configurable. No client busy retry, universal hardcoded60 seconds or fabricated successful send. Native four-hour resend policy is a real gap, not permission to shorten, backdate or bypass it.

6. **Logout:** Supabase defaults to `global`; `local` affects the current session, `others` preserves the current session. Successful global/local signout clears owned local auth storage and notifies local signout; `others` does not produce the current client's `SIGNED_OUT`. Global revokes all refresh sessions, but already-issued access JWTs can remain usable until expiry; remote devices do not instantly receive an event merely from server revocation. Test exact storage/event/sibling-session effects, not immediate JWT invalidation. Our native303/manual redirect, even when refresh sessions are actually gone, is **not an authenticated SDK acknowledgement**: retain the honest unconfirmed error. Do not silently succeed for unsupported `others` or add redirect-follow credentials.
